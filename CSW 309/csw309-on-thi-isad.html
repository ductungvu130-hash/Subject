Ôn thi thực hành CSW 309 — từ đề bài ra tới bản vẽ hoàn chỉnh

3 đề thi giữa kỳ đều theo đúng một khuôn: Section 1 (Problem, Functional Requirements, Use Case) rồi Section 2 (DFD Level-0, ERD). Học công thức 1 lần — áp được cho mọi scenario khác nhau. Trang này đi từng bước: cách đọc đề để "bốc" ra process/entity/data store, quy tắc vẽ đúng chuẩn, và lời giải đầy đủ của cả 3 đề thật.

Tổng quan

Cấu trúc đề thi — 100 điểm, 5 câu

Cả 3 đề (Q1, Q2, Q3) đều bổ đôi giống hệt nhau. Nhớ đúng bảng này là biết mình cần viết bao nhiêu, vẽ bao nhiêu.

Mấu chốt Đề luôn cho sẵn nguyên liệu

Scenario nào cũng có sẵn 2 khối: "System users" và "Main processes" ngay trong đề. Đừng tự nghĩ ra — đó chính là External Entities và Processes của DFD, cũng là Actors và Use Cases của UC Diagram. Việc của mình là chuyển đổi đúng định dạng, không phải sáng tác thêm.

Section 1 · Question 1 — 10 điểm

Problem Description & System Request

Yêu cầu luôn 3 phần: Problem (vì sao cần hệ thống) → Goal → 2–3 Benefits. Đọc đoạn scenario, gạch chân các câu than phiền — đó là nguyên liệu cho Problem.

Problem: Currently, [cách làm thủ công hiện tại] leads to [hậu quả: errors / delays / double booking / confusion]. Goal: The company wants to develop a computerized system that allows [user] to [làm gì], and allows [user khác] to [làm gì]. Benefits: - Reduce [lỗi/thời gian] - Faster / more accurate [process] - Centralized data for [tra cứu / báo cáo / quản lý]

Kỹ thuật đọc nhanh (30 giây)

Trong đoạn mở đầu scenario luôn có 2–3 câu chứa từ khóa "vấn đề". Chỉ cần bắt đúng các cụm: errors and delays, double bookings, long waiting time, confusion, no centralized record — ghép lại thành câu Problem là xong, không cần văn hoa.

Section 1 · Question 2 — 10 điểm

Functional Requirements

Đây là câu "free điểm" nhất đề — vì list Main processes trong scenario gần như đã là đáp án, chỉ cần viết lại đúng văn phong requirement.

The system shall allow [actor] to [verb + main process].

Quy tắc Biến "Main processes" → "Functional Requirements"

Mỗi process trong đề = 1 requirement. Nếu đề yêu cầu 5–6 chức năng mà scenario chỉ liệt kê 4 main processes, tách nhỏ 1 process thành 2 câu (ví dụ "Manage Course Information" → tách "add/update course" và "delete course") hoặc thêm requirement hợp lý về xem báo cáo / thông báo mà đoạn văn scenario có nhắc tới nhưng không nằm trong list chính thức.

shall allow ... to view shall allow ... to manage (add/edit/delete) shall allow ... to search / filter shall allow ... to submit / request shall allow ... to approve / reject shall notify ... when
Section 1 · Question 3 — 20 điểm

Use Case Diagram

Actor = System users. Use case = Main processes (đã ghi sẵn trong Q2). Vẽ không khó, chỉ cần đúng ký hiệu và đúng ai-kết-nối-với-cái-gì.

Ví dụ: Use Case Diagram đề Q1 (Training Center) — Staff nối cả 4 use case, Student chỉ nối "Register for Course"

4 ký hiệu bắt buộc

  • Actor — hình người que, đặt ngoài khung hệ thống
  • System boundary — hình chữ nhật bao toàn bộ use case, ghi tên hệ thống trên đầu
  • Use case — hình oval, đặt trong khung, 1 oval = 1 chức năng chính
  • Association — đường thẳng nối actor với use case (không mũi tên)

Lỗi hay gặp Bị trừ điểm oan

  • Quên vẽ system boundary → mất điểm setup
  • Actor tự nối actor, hoặc use case tự nối use case
  • Thiếu use case so với list Functional Requirements đã liệt kê ở Q2
  • 1 actor không nối use case nào (actor "mồ côi")

Nếu dư thời gian <<include>> / <<extend>>

Ví dụ đề canteen: "Place Order" <<include>> "Make Payment" (luôn xảy ra cùng nhau). Đề library: "Submit Booking Request" <<extend>> bởi bước phụ nếu cần — không bắt buộc nhưng có thể lấy điểm cộng nếu thời gian còn.

Section 2 · Question 1 — 30 điểm

Data Flow Diagram — Level 0

Câu nặng điểm nhất đề. Cần đúng 4 loại ký hiệu, đúng số lượng tối thiểu đề yêu cầu (thường: ≥3 process, ≥2 data store, ≥2 external entity), và tuân thủ luật kết nối.

Cách xác định Từ đề bài ra thẳng 3 thành phần

Thành phầnLấy từ đâu trong đề
External EntityNguyên list "System users" — copy y nguyên (Student, Staff, Manager...)
ProcessNguyên list "Main processes" — đánh số 1.0, 2.0, 3.0...
Data StoreĐề hay cho sẵn ví dụ trong ngoặc (e.g., D1: Student Data, D2: Course Data) — nếu không có, tự đặt tên = "dữ liệu mà process cần lưu lại"

4 luật bất di bất dịch

  • Data Store không nối thẳng với External Entity — phải qua 1 Process
  • External Entity không nối thẳng với External Entity khác
  • Data Store không nối thẳng với Data Store khác
  • Mỗi Process phải có ít nhất 1 flow vào và 1 flow ra (không có "black hole" hoặc "miracle")

Thứ tự vẽ trong 5 phút

  1. Viết External Entities ở 2 mép trái/phải tờ giấy
  2. Đặt các Process ở giữa, theo đúng thứ tự luồng nghiệp vụ (process nào xảy ra trước vẽ trước)
  3. Đặt Data Store ngay cạnh Process nào đọc/ghi vào nó
  4. Đọc lại từng câu trong đoạn mô tả scenario, mỗi câu = 1 mũi tên data flow có label (không để mũi tên trống tên)
  5. Đếm lại: đủ số process/store/entity tối thiểu đề yêu cầu chưa?
Section 2 · Question 2 — 30 điểm

Entity–Relationship Diagram

Đề luôn gợi ý sẵn entity tối thiểu trong ngoặc, ví dụ "(Student, Course, Registration)". Việc còn lại: thêm attribute, gạch chân PK, và vẽ đúng cardinality.

Quan hệ nhiều–nhiều Student↔Course được giải quyết qua bảng trung gian Registration

Cách xác định entity

  • Danh từ chính có dữ liệu riêng, cần lưu trữ độc lập (Student, Room, Order...)
  • Nếu 2 entity có quan hệ nhiều–nhiều (n–n), luôn cần 1 entity trung gian (Registration, OrderDetail, Booking) để tách thành 2 quan hệ 1–n
  • Mỗi entity ít nhất 1 PK + 2–3 attribute mô tả hợp lý theo ngữ cảnh

Cardinality — hỏi 2 câu

Với mỗi cặp entity, tự hỏi:

  • "1 Student có thể có bao nhiêu Booking?" → nhiều → phía Booking ghi *
  • "1 Booking thuộc về bao nhiêu Student?" → 1 → phía Student ghi 1

PK bên "1" luôn xuất hiện làm FK ở bên "nhiều".

UML

Class Diagram

Class Diagram cùng "nguyên liệu" với ERD (entity → class) nhưng thêm method (hành vi) và visibility, đồng thời thể hiện quan hệ theo kiểu hướng đối tượng (association / aggregation / composition / generalization) thay vì chỉ cardinality dữ liệu.

Class box 3 tầng: tên class / thuộc tính (− private) / phương thức (+ public) — quan hệ association ghi rõ tên + cardinality 2 đầu

Chuyển từ ERD sang Class nhanh

  • Entity → Class, giữ nguyên attribute (bỏ chữ PK/FK, chỉ cần liệt kê tên + kiểu dữ liệu)
  • Thêm 2–3 method hợp lý theo đúng Functional Requirements đã viết ở Q2 (VD: entity Booking → method approve(), cancel())
  • Quan hệ nhiều–nhiều: có thể giữ trực tiếp *..* giữa 2 class (không bắt buộc tách bảng trung gian như ERD), hoặc tách thành class riêng nếu nó có thuộc tính/method riêng (VD: Registration có registrationDate, status → nên tách thành class)

Ký hiệu quan hệ cần nhớ

Quan hệKý hiệu đường nốiÝ nghĩa
Associationđường thẳng2 class liên quan nhau, có thể ghi cardinality
Aggregationđường + hình thoi rỗng"has-a", phần có thể tồn tại độc lập (Room chứa nhiều Booking)
Compositionđường + hình thoi đặc"phần thuộc hẳn về tổng", mất tổng thì mất phần (Order — OrderDetail)
Generalizationđường + tam giác rỗngkế thừa (Staff, Manager cùng kế thừa từ class User)

Áp nhanh vào 3 đề

ĐềClass chínhMethod tiêu biểu
Training CenterStudent, Course, RegistrationStudent.register(course), Staff.manageCourse()
Canteen AppStudent, MenuItem, Order, PaymentOrder.placeOrder(), Payment.pay(), Order.updateStatus()
Library BookingStudent, Room, BookingStudent.submitBooking(), Staff.approveBooking(), Manager.generateReport()

Lưu ý: 3 đề gốc chỉ chấm điểm ERD, không yêu cầu Class Diagram riêng — phần này để ôn thêm phòng khi đề đổi format hoặc để hiểu sâu hơn quan hệ hướng đối tượng giữa các entity.

Kỹ năng phòng thi

Thao tác drawio nhanh — tiết kiệm 10–15 phút

90 phút cho 5 câu, phần vẽ chiếm 50/100 điểm — thao tác chuột chậm là mất điểm oan vì hết giờ.

Tìm shape nhanh

Double-click vùng trống trên canvas → gõ tên shape (actor, process, data store, entity) → Enter. Nhanh hơn nhiều so với kéo từ panel bên trái.

Panel có sẵn stencil

Bên trái tìm mục "UML" (có sẵn Actor, Use Case, boundary) và "Entity Relation" (có sẵn khung ERD 3 dòng: tên bảng / PK / attribute) — bật lên từ "More Shapes" nếu chưa thấy.

Phím tắt sống còn

  • Ctrl+D — nhân bản shape (dùng cho nhiều oval use case / nhiều entity box giống layout)
  • Ctrl+Shift+H — fit toàn bộ diagram vào màn hình
  • Kéo cạnh shape ra sẽ tự hiện mũi tên nối — không cần chọn riêng công cụ Line
  • Double-click giữa đường nối để thêm label ngay trên arrow

Luyện đề

3 đề thi thật — lời giải đầy đủ từng câu

Chọn đề để xem breakdown Actor/Process/Data Store/Entity theo đúng format điểm số của đề đó.

Scenario tóm tắt

Đăng ký khóa học thủ công bằng giấy, staff nhập tay vào Excel → lỗi, chậm trễ. Users: Staff, Student. Yêu cầu tối thiểu: DFD ≥3 process / 2 store / 2 entity; ERD ≥3 entity (Student, Course, Registration).

Q1 — Problem & Goal

Problem: Students currently register by filling paper forms; staff manually enter data into Excel, causing errors and delays.

Goal: Build a simple computerized system for staff to manage course/student info and register students; students can view registration lists.

Benefits: Fewer data-entry errors, faster registration, easier tracking/reporting.

Q2 — Functional Requirements (5)

  • Allow Staff to manage course information
  • Allow Staff to manage student information
  • Allow Student to request registration for a course
  • Allow Staff to register students into available courses
  • Allow Staff to view course registration lists

Q3 — Use Case

Actors: Staff, Student. Use cases: Manage Course Info, Manage Student Info, Register for Course (Student khởi tạo request, Staff xử lý), View Registration List (Staff).

Section 2.1 — DFD Level-0

External Entities: Staff, Student

Processes: 1.0 Manage Course Info · 2.0 Manage Student Info · 3.0 Register Student for Course · 4.0 View Registration List

Data Stores: D1 Student Data · D2 Course Data

Section 2.2 — ERD

Student(StudentID PK, Name, Email, Phone)

Course(CourseID PK, CourseName, Schedule, Capacity)

Registration(RegID PK, StudentID FK, CourseID FK, RegDate) — Student 1—* Registration *—1 Course

Scenario tóm tắt

Sinh viên xếp hàng mua đồ ăn ở canteen, dễ nhầm order, khó theo dõi đơn đã trả tiền. Users: Canteen Staff, Student. Yêu cầu tối thiểu: DFD ≥3 process / 2 store / 2 entity; ERD gợi ý Student, Order, Menu-Item, Payment.

Q1 — Problem & Goal

Problem: Students queue and order verbally at the counter, causing mistakes, long wait times, and confusion over which orders are paid.

Goal: A mobile app where students select food, place orders, pay in-app, and get a "ready to collect" notice; staff manage menu and update order status.

Benefits: Shorter wait time, fewer order mistakes, clear payment/order tracking.

Q2 — Functional Requirements (5)

  • Allow Student to browse menu and prices
  • Allow Student to place a food order
  • Allow Student to pay inside the app
  • Allow Student to receive "order ready" notification
  • Allow Canteen Staff to view paid orders and update order status

Q3 — Use Case

Actors: Canteen Staff, Student. Use cases: Browse Menu, Place Order <<include>> Make Payment, Receive Notification, Manage Menu (Staff), Update Order Status (Staff).

Section 2.1 — DFD Level-0

External Entities: Student, Canteen Staff

Processes: 1.0 Manage Menu Info · 2.0 Place Food Order & Make Payment · 3.0 Update Order Status / Notify Student

Data Stores: D1 Menu Data · D2 Orders & Payments Data

Section 2.2 — ERD

Student(StudentID PK, Name)

MenuItem(ItemID PK, Name, Price)

Order(OrderID PK, StudentID FK, OrderDate, Status)

Payment(PaymentID PK, OrderID FK, Amount, Method) — Student 1—* Order 1—1 Payment; Order *—* MenuItem

Scenario tóm tắt

Đặt phòng thư viện thủ công qua sổ/Excel → double booking, sinh viên không rõ trạng thái đặt phòng. Users: Student, Library Staff, Library Manager. Yêu cầu tối thiểu: DFD ≥5 process / 3 store / 3 entity; ERD gợi ý Student, Room, Booking.

Q1 — Problem & Goal

Problem: Bookings are recorded manually in notebooks/Excel, causing double bookings; students can't confirm status without repeated inquiries; no centralized usage data.

Goal: A computerized system for students to check availability and book online; staff manage schedules and confirm/reject bookings; track room usage.

Benefits: No more double bookings, faster confirmation, centralized usage reports for planning.

Q2 — Functional Requirements (6)

  • Allow Student to search room availability
  • Allow Student to submit a booking request online
  • Allow Library Staff to manage room information
  • Allow Library Staff to approve or reject bookings
  • Allow Student to view booking status
  • Allow Library Manager to generate room usage reports

Q3 — Use Case

Actors: Student, Library Staff, Library Manager. Use cases: Search Room Availability, Submit Booking Request, View Booking Status (Student) · Manage Room Info, Approve/Reject Booking (Staff) · Generate Usage Report (Manager).

Section 2.1 — DFD Level-0

External Entities: Student, Library Staff, Library Manager

Processes: 1.0 Manage Room Info · 2.0 Search Room Availability · 3.0 Submit Booking Request · 4.0 Approve/Reject Booking · 5.0 View Booking Status · 6.0 Generate Usage Report

Data Stores: D1 User Data · D2 Room Data · D3 Booking Data

Section 2.2 — ERD

Student(StudentID PK, Name, Email, Phone)

Room(RoomID PK, RoomName, Capacity, Location)

Booking(BookingID PK, StudentID FK, RoomID FK, BookingDate, TimeSlot, Status) — Student 1—* Booking *—1 Room
