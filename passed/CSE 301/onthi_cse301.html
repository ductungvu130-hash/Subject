SELECT & WHERE — Truy vấn cơ bản

Cú pháp SELECT đầy đủ

sql
SELECT   cột1, cột2, COUNT(*), SUM(cột)
FROM     bảng
JOIN     bảng2 ON điều_kiện_join
WHERE    điều_kiện_lọc_hàng          -- lọc TRƯỚC group by
GROUP BY cột_nhóm
HAVING   điều_kiện_lọc_nhóm         -- lọc SAU group by
ORDER BY cột ASC/DESC
LIMIT    n;
💡 Thứ tự thực thi SQL
FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
Nhớ thứ tự này để hiểu tại sao không dùng alias của SELECT trong WHERE được.

Ví dụ JOIN 3 bảng (TechNova)

sql — Lấy chi tiết đơn hàng kèm tên khách và tên sản phẩm
SELECT
    c.full_name,
    p.product_name,
    od.quantity,
    od.unit_price,
    od.quantity * od.unit_price AS line_total
FROM   order_header oh
JOIN   customer     c  ON c.customer_id = oh.customer_id
JOIN   order_detail od ON od.order_id   = oh.order_id
JOIN   product      p  ON p.product_id = od.product_id
WHERE  oh.status = 'completed';
⚠️ Chú ý khi JOIN nhiều bảng
Khi JOIN cả order_detail (nhiều dòng) lẫn payment (nhiều dòng) vào cùng 1 query → tích Descartes xảy ra, kết quả bị nhân đôi/sai. Dùng subquery riêng để tính từng phần.

Ví dụ: Báo cáo mua hàng theo khách

sql
SELECT
    c.full_name,
    COUNT(oh.order_id)      AS total_orders,
    SUM(oh.total_amount)   AS total_spent
FROM   customer     c
JOIN   order_header oh ON c.customer_id = oh.customer_id
GROUP BY c.customer_id, c.full_name
HAVING   COUNT(oh.order_id) >= 2
ORDER BY total_spent DESC;

Subquery — Truy vấn lồng nhau

3 dạng Subquery hay gặp trong đề thi

1. Subquery trong WHERE với IN

sql — Khách hàng đã mua Laptop
SELECT customer_id, full_name
FROM   customer
WHERE  customer_id IN (
    SELECT oh.customer_id
    FROM   order_header oh
    JOIN   order_detail od ON oh.order_id = od.order_id
    JOIN   product      p  ON od.product_id = p.product_id
    WHERE  p.category = 'Laptop'
);

2. Subquery trong SELECT (Scalar Subquery)

sql — Tính tổng thanh toán cho mỗi đơn
SELECT
    oh.order_id,
    (SELECT COALESCE(SUM(amount), 0)
     FROM payment p
     WHERE p.order_id = oh.order_id) AS total_paid
FROM order_header oh;

3. Kết hợp OR với 2 subquery (dạng High-Value Customer)

sql
SELECT DISTINCT c.customer_id, c.full_name, c.email
FROM customer c
WHERE
    -- Điều kiện 1: mua Laptop ít nhất 1 lần
    c.customer_id IN (
        SELECT oh.customer_id
        FROM order_header oh
        JOIN order_detail od ON oh.order_id = od.order_id
        JOIN product p      ON od.product_id = p.product_id
        WHERE p.category = 'Laptop'
    )
    OR
    -- Điều kiện 2: tổng chi tiêu > 100 triệu
    c.customer_id IN (
        SELECT customer_id
        FROM order_header
        GROUP BY customer_id
        HAVING SUM(total_amount) > 100000000
    );
✅ Mẹo: Khi nào dùng SELECT DISTINCT?
Khi một khách có thể thỏa cả hai điều kiện OR → họ sẽ xuất hiện 2 lần → dùng DISTINCT để loại trùng.

VIEW — Bảng ảo

View là một câu SELECT được đặt tên, lưu trong DB. Mỗi lần query view, MySQL chạy lại SELECT đó.

sql — Cú pháp tạo View
CREATE VIEW tên_view AS
SELECT
    cột1,
    cột2,
    SUM(quantity * unit_price) AS total_amount
FROM   bảng
JOIN   bảng2 ON ...
GROUP BY ...;

-- Sửa view:
CREATE OR REPLACE VIEW tên_view AS ...;

-- Dùng view:
SELECT * FROM tên_view;
⚠️ Chú ý JOIN nhiều bảng trong View
Nếu join order_detail (n dòng/đơn) + payment (m dòng/đơn) trực tiếp → tích Descartes sai.
Giải pháp: dùng scalar subquery cho từng tổng.

Pattern đúng cho v_order_invoice

sql — Dùng subquery tránh tích Descartes
CREATE VIEW v_order_invoice AS
SELECT
    oh.order_id,
    c.full_name                               AS customer_name,
    oh.order_date,
    (SELECT SUM(od.quantity * od.unit_price)
     FROM order_detail od
     WHERE od.order_id = oh.order_id)           AS total_product_amount,
    (SELECT COALESCE(SUM(p.amount), 0)
     FROM payment p
     WHERE p.order_id = oh.order_id)            AS total_payment,
    (SELECT SUM(od.quantity * od.unit_price)
     FROM order_detail od
     WHERE od.order_id = oh.order_id)
    - (SELECT COALESCE(SUM(p.amount), 0)
       FROM payment p
       WHERE p.order_id = oh.order_id)          AS balance
FROM   order_header oh
JOIN   customer     c ON c.customer_id = oh.customer_id;

Stored Procedure — Thủ tục lưu trữ

sql — Cú pháp đầy đủ
DELIMITER $$

CREATE PROCEDURE tên_procedure(
    IN  p_param1  INT,
    IN  p_param2  VARCHAR(50),
    OUT p_result  INT        -- tham số đầu ra (ít gặp trong đề)
)
BEGIN
    -- 1. Khai báo biến cục bộ
    DECLARE v_stock   INT;
    DECLARE v_price   DECIMAL(15,2);
    DECLARE v_new_id  INT;

    -- 2. Gán biến từ query
    SELECT stock_quantity, unit_price
    INTO   v_stock, v_price
    FROM   product
    WHERE  product_id = p_param1;

    -- 3. Kiểm tra điều kiện → báo lỗi nếu sai
    IF v_stock < p_param2 THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Insufficient stock';
    END IF;

    -- 4. Thực hiện thao tác
    INSERT INTO order_header (customer_id, order_date, status, total_amount)
    VALUES (p_param1, CURDATE(), 'pending', 0);

    SET v_new_id = LAST_INSERT_ID();

    UPDATE product
    SET    stock_quantity = stock_quantity - p_param2
    WHERE  product_id = p_param1;

END $$

DELIMITER ;
LệnhÝ nghĩa
DECLARE v_name TYPE;Khai báo biến cục bộ
SELECT ... INTO v_nameGán kết quả query vào biến
SET v_name = value;Gán trực tiếp
LAST_INSERT_ID()Lấy ID vừa INSERT
SIGNAL SQLSTATE '45000'Ném lỗi tùy chỉnh
IF ... THEN ... END IF;Điều kiện
CURDATE()Ngày hiện tại
Section 2 · SQL Advanced

Trigger — Tự động thực thi

Trigger là code tự chạy khi có sự kiện INSERT/UPDATE/DELETE trên một bảng.

sql — Cú pháp Trigger
DELIMITER $$

CREATE TRIGGER tên_trigger
AFTER INSERT ON bảng        -- BEFORE/AFTER  +  INSERT/UPDATE/DELETE
FOR EACH ROW
BEGIN
    -- NEW.cột  → giá trị mới (INSERT / UPDATE)
    -- OLD.cột  → giá trị cũ  (UPDATE / DELETE)

    DECLARE v_status VARCHAR(20);

    SELECT status INTO v_status
    FROM order_header
    WHERE order_id = NEW.order_id;

    IF v_status != 'cancelled' THEN
        UPDATE order_header
        SET    total_amount = (
            SELECT SUM(quantity * unit_price)
            FROM   order_detail
            WHERE  order_id = NEW.order_id
        )
        WHERE  order_id = NEW.order_id;
    END IF;
END $$

DELIMITER ;
Sự kiệnThời điểmỨng dụng điển hình
BEFORE INSERTTrước khi thêmValidate dữ liệu, chặn lỗi
AFTER INSERTSau khi thêmCập nhật bảng liên quan
BEFORE UPDATETrước khi sửaValidate, tính toán trước
AFTER UPDATESau khi sửaAudit log
BEFORE DELETETrước khi xóaChặn xóa nếu còn liên kết
🚫 SIGNAL trong Trigger
Muốn báo lỗi và hủy thao tác → dùng BEFORE trigger + SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'lỗi'.
Trong AFTER trigger, dữ liệu đã được ghi rồi nên không chặn được.
Section 3 · Optimization

Index & Tối ưu hiệu năng

Tạo Index

sql
-- Index đơn giản trên 1 cột
CREATE INDEX idx_order_date ON order_header(order_date);

-- Index kết hợp nhiều cột (composite)
CREATE INDEX idx_status_date ON order_header(status, order_date);

-- Unique index (kèm ràng buộc không trùng)
CREATE UNIQUE INDEX idx_email ON customer(email);

Tại sao hàm hủy Index?

❌ Query KHÔNG dùng được Index
WHERE YEAR(order_date) = 2025         -- Bọc hàm → index vô dụng
WHERE MONTH(order_date) = 6           -- Tương tự
WHERE DATE_FORMAT(order_date, ...) = x -- Tương tự
✅ Query CÓ thể dùng Index
WHERE order_date BETWEEN '2025-01-01' AND '2025-12-31'
WHERE order_date >= '2025-01-01' AND order_date < '2026-01-01'

Giải thích: Index B-tree lưu trữ giá trị nguyên bản của cột order_date. Khi dùng YEAR(order_date), MySQL phải tính hàm cho mọi hàng rồi mới so sánh → không thể "nhảy thẳng" vào index → full table scan. Dùng BETWEEN thì MySQL tra trực tiếp trên index B-tree.

Ràng buộc dữ liệu (Constraint)

sql — Các loại constraint DDL
-- 1. NOT NULL
full_name VARCHAR(100) NOT NULL,

-- 2. UNIQUE
CONSTRAINT uq_email UNIQUE (email),

-- 3. CHECK (MySQL 8+)
CONSTRAINT chk_price CHECK (unit_price > 0),

-- 4. FOREIGN KEY
CONSTRAINT fk_order_cust
    FOREIGN KEY (customer_id) REFERENCES customer(customer_id),

-- 5. Thêm constraint sau khi tạo bảng
ALTER TABLE payment
ADD CONSTRAINT uq_one_payment UNIQUE (order_id);

Q2

Báo cáo mua hàng theo khách: full_name, total_orders, total_spent — ít nhất 2 đơn — sắp theo total_spent giảm

15 đ
Đáp án
sql
SELECT
    c.full_name,
    COUNT(oh.order_id)    AS total_orders,
    SUM(oh.total_amount)  AS total_spent
FROM   customer     c
JOIN   order_header oh ON c.customer_id = oh.customer_id

S2·Q1

Tạo View v_order_invoice: order_id, customer_name, order_date, total_product_amount, total_payment, balance

10 đ
Đáp án
sql
CREATE VIEW v_order_invoice AS
SELECT
    oh.order_id,
    c.full_name                                      AS customer_name,
    oh.order_date,
    (SELECT SUM(od.quantity * od.unit_price)
     FROM   order_detail od
     WHERE  od.order_id = oh.order_id)               AS total_product_amount,
    (SELECT COALESCE(SUM(p.amount), 0)
     FROM   payment p
     WHERE  p.order_id = oh.order_id)                AS total_payment,
    (SELECT SUM(od.quantity * od.unit_price)
     FROM   order_detail od
     WHERE  od.order_id = oh.order_id)
    -(SELECT COALESCE(SUM(p.amount), 0)
      FROM   payment p
      WHERE  p.order_id = oh.order_id)               AS balance
FROM   order_header oh
JOIN   customer     c ON c.customer_id = oh.customer_id;
Tại sao dùng scalar subquery?
Nếu JOIN thẳng order_detail + payment vào: với đơn có 3 sản phẩm và 2 thanh toán → 3×2 = 6 hàng → SUM bị sai (nhân đôi).
Scalar subquery tính riêng từng phần → không bị tích Descartes.

COALESCE(SUM(amount), 0) — khi đơn chưa có thanh toán, SUM trả NULL → COALESCE đổi thành 0.
S2·Q2

Stored Procedure sp_create_order(p_customer_id, p_product_id, p_quantity)

15 đ
Kiểm tra tồn kho. Nếu không đủ → lỗi "Insufficient stock". Nếu đủ → Insert order_header + order_detail + Update tồn kho.
Đáp án
sql
DELIMITER $$

CREATE PROCEDURE sp_create_order(
    IN p_customer_id  INT,
    IN p_product_id   INT,
    IN p_quantity     INT
)
BEGIN
    DECLARE v_stock    INT;
    DECLARE v_price    DECIMAL(15,2);
    DECLARE v_order_id INT;

    -- Bước 1: Lấy thông tin sản phẩm
    SELECT stock_quantity, unit_price
    INTO   v_stock, v_price
    FROM   product
    WHERE  product_id = p_product_id;

    -- Bước 2: Kiểm tra tồn kho
    IF v_stock < p_quantity THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Insufficient stock';
    END IF;

    -- Bước 3: Tạo đơn hàng
    INSERT INTO order_header (customer_id, order_date, status, total_amount)
    VALUES (p_customer_id, CURDATE(), 'pending', 0);

    SET v_order_id = LAST_INSERT_ID();

    -- Bước 4: Thêm chi tiết đơn
    INSERT INTO order_detail (order_id, product_id, quantity, unit_price)
    VALUES (v_order_id, p_product_id, p_quantity, v_price);

    -- Bước 5: Cập nhật tồn kho
    UPDATE product
    SET    stock_quantity = stock_quantity - p_quantity
    WHERE  product_id = p_product_id;

END $$

DELIMITER ;
Luồng logic: Lấy tồn kho → So sánh → Báo lỗi nếu thiếu → Insert order_header → Dùng LAST_INSERT_ID() lấy order_id vừa tạo → Insert order_detail → Trừ tồn kho.

total_amount = 0 ban đầu vì Trigger (Q3 section 2) sẽ tự cập nhật sau khi INSERT order_detail.

S3·Q1

Ngăn thanh toán vượt total_amount của đơn hàng

10 đ
a) Viết constraint hoặc trigger ngăn tổng thanh toán vượt total_amount trong order_header. b) Giải thích cơ chế.
Đáp án — a) Trigger BEFORE INSERT
sql
DELIMITER $$

CREATE TRIGGER trg_check_payment_limit
BEFORE INSERT ON payment
FOR EACH ROW
BEGIN
    DECLARE v_total_amount DECIMAL(15,2);
    DECLARE v_paid         DECIMAL(15,2);

    -- Lấy tổng tiền cần trả của đơn
    SELECT total_amount INTO v_total_amount
    FROM   order_header
    WHERE  order_id = NEW.order_id;

    -- Lấy tổng đã thanh toán từ trước
    SELECT COALESCE(SUM(amount), 0) INTO v_paid
    FROM   payment
    WHERE  order_id = NEW.order_id;

    -- Nếu tổng sau khi thêm > total_amount → chặn
    IF v_paid + NEW.amount > v_total_amount THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Payment exceeds order total amount';
    END IF;
END $$

DELIMITER ;
b) Giải thích
Cơ chế toàn vẹn dữ liệu:
1. Trigger kích hoạt TRƯỚC mỗi lần INSERT vào bảng payment.
2. Tính tổng đã thanh toán (v_paid) từ các bản ghi payment hiện có.
3. Kiểm tra: v_paid + NEW.amount > v_total_amount?
4. Nếu đúng → SIGNAL ném lỗi, MySQL hủy INSERT → dữ liệu KHÔNG được ghi.
5. Kết quả: Không bao giờ có tình trạng tổng thanh toán vượt giá trị đơn hàng.
S3·Q2

Tối ưu query với 15 triệu bản ghi — Index và hàm làm hỏng Index

10 đ
a) Tạo Index tối ưu: WHERE order_date BETWEEN '2025-01-01' AND '2025-12-31'. b) Giải thích tại sao WHERE YEAR(order_date) = 2025 không dùng được index.
a) Tạo Index
sql
CREATE INDEX idx_order_date
    ON order_header(order_date);
b) Giải thích
Câu truy vấn tốt (dùng được index):
WHERE order_date BETWEEN '2025-01-01' AND '2025-12-31'
→ MySQL tra thẳng vào B-tree index trên cột order_date, tìm vị trí bắt đầu rồi quét đến cuối range → rất nhanh.

Câu truy vấn chậm (KHÔNG dùng được index):
WHERE YEAR(order_date) = 2025
→ MySQL phải gọi hàm YEAR() trên từng hàng trong 15 triệu bản ghi, rồi mới so sánh. Index lưu giá trị gốc của order_date, không lưu YEAR(order_date) → không dùng được → Full Table Scan → cực chậm.

Nguyên tắc: Không bao giờ bọc cột được index trong hàm ở vế WHERE.

Đáp án
sql
CREATE VIEW v_booking_details AS
SELECT
    b.booking_id,
    g.full_name                                           AS guest_full_name,
    r.room_number,
    b.check_in_date,
    b.check_out_date,
    r.price_per_night
        * DATEDIFF(b.check_out_date, b.check_in_date)     AS room_price,
    (SELECT COALESCE(SUM(su.quantity * s.unit_cost), 0)
     FROM   service_usage su
     JOIN   service       s  ON su.service_id = s.service_id
     WHERE  su.booking_id = b.booking_id)                  AS service_fee
FROM   booking b
JOIN   guest   g ON g.guest_id = b.guest_id
JOIN   room    r ON r.room_id  = b.room_id;
DATEDIFF(check_out, check_in) = số đêm ở → nhân price_per_night = room_price.
Scalar subquery cho service_fee tránh tích Descartes giữa service_usage và booking.

Stored Procedure sp_add_service_usage(p_booking_id, p_service_id, p_quantity)

Kiểm tra booking_id tồn tại. Nếu không → lỗi "Booking is cancelled". Nếu hợp lệ → INSERT vào service_usage.
Đáp án
sql
DELIMITER $$

CREATE PROCEDURE sp_add_service_usage(
    IN p_booking_id  INT,
    IN p_service_id  INT,
    IN p_quantity    INT
)
BEGIN
    DECLARE v_count INT;

    -- Kiểm tra booking tồn tại
    SELECT COUNT(*) INTO v_count
    FROM   booking
    WHERE  booking_id = p_booking_id;

    IF v_count = 0 THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Booking is cancelled';
    END IF;

    -- Thêm dịch vụ
    INSERT INTO service_usage (booking_id, service_id, quantity)
    VALUES (p_booking_id, p_service_id, p_quantity);

END $$

DELIMITER ;
S2·Q3

Trigger trg_update_room_status: AFTER INSERT on booking — Đổi phòng thành 'occupied'

15 đ
Event: AFTER INSERT on booking. Action: UPDATE status = 'occupied'. Condition: chỉ nếu check_in_date là hôm nay hoặc trước.
Đáp án
sql
DELIMITER $$

CREATE TRIGGER trg_update_room_status
AFTER INSERT ON booking
FOR EACH ROW
BEGIN
    -- Chỉ cập nhật khi check_in_date là hôm nay hoặc đã qua
    IF NEW.check_in_date <= CURDATE() THEN
        UPDATE room
        SET    status = 'occupied'
        WHERE  room_id = NEW.room_id;
    END IF;
END $$

DELIMITER ;
CURDATE() trả về ngày hiện tại (không có giờ).
NEW.check_in_date <= CURDATE() — đặt phòng cho hôm nay hoặc quá khứ → phòng đã được sử dụng → cập nhật 'occupied'.
Nếu đặt cho tương lai → không thay đổi status (giữ 'available').

S3·Q1

Ngăn Double Booking: không cho đặt phòng đã có booking 'confirmed' chồng chéo thời gian

10 đ
a) Trigger BEFORE INSERT
sql
DELIMITER $$

CREATE TRIGGER trg_prevent_double_booking
BEFORE INSERT ON booking
FOR EACH ROW
BEGIN
    DECLARE v_overlap INT;

    -- Đếm xem có booking nào chồng chéo thời gian không
    SELECT COUNT(*) INTO v_overlap
    FROM   booking
    WHERE  room_id        = NEW.room_id
      -- Điều kiện chồng chéo: [new_in, new_out) giao [existing_in, existing_out)
      AND  NEW.check_in_date  < check_out_date
      AND  NEW.check_out_date > check_in_date;

    IF v_overlap > 0 THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Room already booked for this period';
    END IF;
END $$

DELIMITER ;
b) Giải thích
Logic chồng chéo thời gian: Hai khoảng [A,B) và [C,D) chồng chéo khi và chỉ khi A < D AND C < B.
→ NEW.check_in < existing.check_out AND NEW.check_out > existing.check_in

Trigger BEFORE INSERT cho phép hủy thao tác trước khi dữ liệu được ghi → đảm bảo không bao giờ có 2 booking cùng phòng cùng thời gian.
S3·Q2

Index cho query YEAR(check_in_date) = 2024 — tại sao không hiệu quả?

10 đ
a) Tạo Index
sql
CREATE INDEX idx_check_in_date
    ON booking(check_in_date);
b) Giải thích tại sao YEAR() không dùng được Index
Index B-tree được tổ chức theo giá trị gốc của cột check_in_date (dạng DATE: 2024-01-01, 2024-01-02, ...).

Khi viết WHERE YEAR(check_in_date) = 2024, MySQL phải:
1. Lấy từng giá trị check_in_date
2. Tính YEAR() cho nó
3. So sánh với 2024
→ Phải duyệt toàn bộ bảng (Full Table Scan), index vô dụng.

Sửa đúng:
WHERE check_in_date >= '2024-01-01' AND check_in_date < '2025-01-01'
→ Dùng được index, cực nhanh với bảng 10M bản ghi.

Checklist trước khi nộp bài

✅ Checklist
  • Mọi alias aggregate (COUNT, SUM) có tên rõ ràng (AS tên)
  • GROUP BY chứa đủ các cột không phải aggregate trong SELECT
  • HAVING thay vì WHERE cho điều kiện aggregate
  • DISTINCT khi có thể trùng do OR giữa 2 subquery
  • COALESCE(SUM(...), 0) khi có thể không có dữ liệu (NULL)
  • DELIMITER $$ ... DELIMITER ; quanh mọi Procedure và Trigger
  • SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '...' cho lỗi tùy chỉnh
  • LAST_INSERT_ID() ngay sau INSERT để lấy ID mới
  • Index: không bọc cột index trong hàm ở WHERE
  • View tránh JOIN nhiều bảng có quan hệ N-N → dùng scalar subquery
